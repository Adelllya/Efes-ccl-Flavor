# Отзывы гостей о парах

Запрос владельца: «добавь отзывы там и их оценки тоже сохранять бы умно обрабатывать». Основа в спецификации —
ENGINE_V2_SPEC.md §7.4, п. 5: «Сбор реакций гостей в приложении ("помогло / нет") → пересчёт раз в спринт».

Коротко, что получилось:

* после подбора гость видит виджет **«Как вам пара?»**: 1–5 звёзд, метки («Слишком горько», «Снимает жирность»…),
  «Подбор помог?» и, если хочет, пару слов;
* метки сразу подстраивают **его личный профиль** (горечь, сладость, чувствительность) — на его телефоне, сервер профиль не хранит;
* оценки складываются в **сводку пары** с поправкой на малое число оценок; текст проходит проверку (ИИ или модератор);
* бар видит отзывы о своих парах в кабинете и список пар «на доработку»;
* устойчивые оценки раз в спринт выгружаются в калибровку движка — как **слабый** сигнал.

Выдуманных отзывов нет нигде: ни в фикстурах, ни в сидах, ни в интерфейсе. Пусто — значит «Оценок пока нет».

---

## Что собираем и зачем

| Поле | Зачем |
|---|---|
| `drink_id`, `dish_id` (или `custom` + `dish_name`) | какую пару оценили; id — из `data/drinks.json` и `data/dishes_v2.json` |
| `rating` 1–5 (обязательно) | главный сигнал |
| `helpful` да / нет / не ответил | «помогло / нет» из §7.4 |
| `chips` — метки из словаря | что именно сработало или нет; двигают личный профиль |
| `text` ≤ 1000 знаков, необязательно | живые формулировки для сомелье и других гостей |
| `locale` | язык интерфейса гостя (ru / kk / en) |
| `venue`, `table_number` | отзыв из заведения попадает в его кабинет |
| `verified` | в этом заведении был скан QR той же сессией за последние 12 ч — такой отзыв весит ×1.5 |
| `score_shown`, `engine_version`, `calibration_version`, `ctx` | какой балл гость видел и при каком движке/поводе — чтобы калибровка сравнивала честно |
| `session_hash`, `ip_hash` | «одна оценка на пару» и лимиты (см. ниже, это не сами данные) |
| `ua_short` | только класс устройства: `ios/safari`, `android/chrome`, `bot` |
| `status`, `heuristics`, `ai_*`, `moderated_at`, `edit_count` | результат обработки текста и решения модератора |

Модель — `PairingReview` (`backend/api/models.py`, миграция `0008_pairing_reviews`). Индекс по (`drink_id`, `dish_id`),
уникальность (`session_hash`, `drink_id`, `dish_key`) и проверка `1 ≤ rating ≤ 5` — на уровне базы.

## Чего НЕ собираем

* **Сырых IP нет.** Храним `HMAC-SHA256(соль, IP)`; соль выводится из `SECRET_KEY`, у IP и у сессии соли разные
  (хеши между собой не сопоставить). Сменили `SECRET_KEY` — старые хеши больше не совпадут, лимиты и «одна оценка на пару»
  начнутся заново; это нормально.
* **Идентификатор сессии** (случайная строка из браузера, та же, что у трекинга меню) — тоже только как HMAC.
* **Имён, телефонов, e-mail нет.** Телефоны (10–15 цифр) и e-mail в тексте заменяются на «[скрыто]» **до записи** в базу.
* **Полный User-Agent не храним** — только «ос/браузер».
* **Flavor DNA гостя с отзывом не сохраняем** — из контекста остаются повод и личные настройки.
* Публично и в кабинете у отзыва только **дата**, без времени и стола: по «стол 5, 21:14» официант узнает гостя.
  Стол видит только сомелье в модерации.

## Как обрабатывается отзыв

```
виджет → POST /api/v2/reviews/
  1. проверка полей (400 с понятным текстом и именем поля)
  2. лимиты по сессии и по IP (429 + Retry-After)
  3. «одна оценка на пару»: та же сессия и пара → правка прежней записи
  4. текст: чистка → маскирование телефонов и e-mail → офлайн-эвристики
  5. если текст новый и ИИ настроен → ИИ-разбор (строгая JSON-схема, таймаут 8 с)
  6. статус: published / pending / spam
  7. ответ: сам отзыв (без хешей) + applied_prefs + свежая сводка пары
```

### Метки → личный профиль гостя (`applied_prefs`)

Профиль — это контекст движка R17: `bitter_pref`, `sweet_pref` (−1…1), `heat_lover`, `harsh_tol`
(tolerant → median → sensitive, множитель штрафов 0.6 / 1.0 / 1.4). Сервер считает поправку, а применяет её
`GuestPrefsService` на устройстве гостя; в базе профиля нет.

| Метка | Поправка профиля | Что говорит о паре (правило движка) |
|---|---|---|
| Идеальная пара | — | пара подтверждена целиком |
| Снимает жирность | — | R2: cut сработал |
| Освежает | — | R9, R16 hot: карбонизация и кислота |
| Гасит остроту | — | R3 relief: сахар, молоко, холод |
| Вкусы перекликаются | — | R10–R12: мосты (у R12 уровень D — гости почти единственный сигнал) |
| Слишком горько | `bitter_pref −0.25` | R17, R14, R7 |
| Слишком сладко | `sweet_pref −0.25` | R17, R4, R14 |
| Жжёт сильнее | `harsh_tol +1`, `heat_lover = false` | R3 aggr (спирт, хмель × капсаицин), V3 |
| Слишком крепко | `harsh_tol +1` | R6 alco, R3 burn, R16 meal |
| Перебивает блюдо | — | R1 / V1: напиток громче блюда |
| Теряется на фоне блюда | — | R1 / V6: блюдо громче напитка |
| Не взял бы снова | — | пара отвергнута |

Словарь с обоснованием каждой метки — `REVIEW_CHIPS` в `backend/api/reviews_logic.py`; во фронтенде — зеркало
в `core/reviews.service.ts` (совпадение проверяет тест).

Почему шаг 0.25: R17 даёт `clamp(14·pref·(B.bitter − 0.5), −7, +7)`, значит один шаг двигает балл напитка максимум
на 1.75. За один отзыв ось сдвигается не больше чем на 0.5, чувствительность — не больше чем на одну ступень:
один неудачный вечер не переворачивает профиль. «Понравилось» профиль не трогает — непонятно, какая ось сработала.

**Правка отзыва не применяется дважды.** Сервер отдаёт только разницу между новой и прошлой версией: сняли метку
«Слишком горько» — придёт `bitter_pref +0.25`. Если ИИ нашёл в тексте явную жалобу («очень горько»), которой нет
в метках, она тоже попадает в поправку, с пометкой `source: "text"` — гость видит «Учли: меньше горечи».
Подсказки офлайн-эвристик (без ИИ) в профиль не идут: у них нет понимания контекста.

### Сводка оценок

```
ожидание в звёздах  = 1 + 4·(балл − 3) / 96          # балл движка 3..99 → 1..5: 51 → 3.0, 75 → 4.0, 99 → 5.0
показанная средняя  = (Σ w·r + m·ожидание) / (Σ w + m),  m = 5
w = 1.5 для отзыва «из заведения», иначе 1
```

* Байесовское сжатие: пока оценок мало, средняя держится около ожидания движка; с ростом числа оценок решают гости.
  Пример: ожидание 3.0, три пятёрки → (15 + 15) / 8 = **3.8**, а не 5.0.
* Ожидание — балл движка для пары в нейтральном контексте (без личных настроек). Для своего блюда движок пару не считает —
  ожидание нейтральное, 3.0. Шкалы разные по смыслу (балл — совместимость по правилам, звёзды — удовольствие гостя),
  поэтому ожидание — только стартовая точка.
* Пока оценок **меньше трёх**, средней нет: «Мало оценок: n». Ноль — «Оценок пока нет».
* **Расхождение с движком**: сырая взвешенная средняя отличается от ожидания на ≥ 1.2 звезды при ≥ 5 оценках.
  Сравниваем сырую, а не сжатую — сжатие само тянет к движку. Это пары, которые сомелье стоит перепробовать.
* «Подбор помог» — доля «да» среди ответивших; метки — сколько раз каждую отметили.
* В сводку идут только **опубликованные** отзывы.

### Текст: офлайн-эвристики и ИИ

Офлайн-эвристики (`reviews_logic.analyze_text`, работают всегда):

* язык: ru / kk / en по письменности и частым словам («Efes Pilsener норм» — это русский);
* ссылки и контакты (http, www, домены, t.me, @ник) — **стоп**: автопубликации нет;
* мат — **стоп**; список короткий и очевидный, отдельной константой `PROFANITY` (ru / en / kk);
* повторы символов и КАПС — мягкие флаги, только подсказка модератору;
* подсказки меток по словам («горчит», «перебивает», «освежает», «жжёт»…) с учётом простого отрицания
  («не горчит», «ащы емес») — сохраняются для модератора.

ИИ-разбор (`backend/api/review_ai.py`) — Claude, та же модель, что у ИИ-сомелье (`api.ai.MODEL`):

* строгая JSON-схема: `sentiment` −1…1, `aspects` — **только** id из словаря меток, `mentions_other_dish`,
  `flags {spam, toxic, offtopic}`, `summary_ru` — нейтральный пересказ до 140 знаков;
* **текст гостя — данные, а не инструкции.** Системный промпт неизменен и прямо это говорит; текст уходит только
  значением JSON-поля в сообщении пользователя; попытка «управлять разбором» — признак спама. Ответ ещё раз проверяется
  у нас: чужие метки отбрасываются, пересказ со ссылкой, контактом или матом не сохраняется;
* отказ классификаторов: включён серверный fallback (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`) —
  Anthropic сам повторяет запрос на рекомендованной модели; если отказалась вся цепочка — отзыв идёт на ручную проверку;
* таймаут 8 с, без автоповторов (гость ждёт ответа на свой POST); один отзыв разбирается не больше трёх раз
  (дальше правки текста смотрит модератор) — чтобы правки не жгли деньги;
* любая ошибка (нет ключа, таймаут, сеть, битый JSON) запрос не роняет — остаются эвристики.

Как выбирается статус:

| Ситуация | Статус |
|---|---|
| без текста | `published` — оценка публикуется сразу |
| ИИ разобрал: спам | `spam` |
| ИИ разобрал: toxic / offtopic, или стоп-эвристика | `pending` |
| ИИ разобрал: всё чисто | `published` |
| ИИ пробовали, но ошибка / таймаут | по эвристикам: стоп → `pending`, иначе `published` |
| модель отказалась (refusal) | `pending` |
| ИИ не настроен или исчерпан лимит разборов | `pending` — текст публикует человек |
| модератор уже скрывал отзыв, а гость переписал текст | не выше `pending` |

«Не по теме» (только сервис, цены, музыка) — не повод скрыть отзыв навсегда, но на странице пары он не нужен:
модератор решает сам. Отзыв, где гость пишет, что ел другое блюдо (`mentions_other_dish`), в калибровку не идёт.

### Модерация

Сомелье (токен `FT_ADMIN_TOKEN` или сотрудник Django — как у остальных `/api/admin/*`) видит очередь «на проверке»
и «спам» со всеми подробностями, кроме хешей: текст, эвристики, разбор ИИ, заведение, стол. Решение — `published`,
`pending`, `hidden` или `spam`. Скрытый или спамный отзыв, который гость потом переписал, снова попадает в очередь.

### Кабинет заведения

`GET /api/cabinet/reviews/` (Bearer-токен кабинета): только отзывы **своего** заведения за период тарифа —
сколько оценок, средняя, «подбор помог», сколько из заведения, сколько текстов на проверке; все пары; частые метки;
последние опубликованные тексты; **пары на доработку** — сжатая средняя ≤ 3 ★ или гости ниже ожидания подбора.
Непроверенных текстов, столов и времени владелец не видит. Блок для SPA — `pages/cabinet/cabinet-reviews.component.ts`.

## Как гостевые оценки попадают в калибровку

```
python manage.py export_guest_pairs              # → data/guest_pairs.json
python manage.py export_guest_pairs --dry-run    # только посчитать
```

* Формат — как `pairs` в `data/test_pairs.json`: `origin: "guests"`, `evidence: "G"`, `split: "train"`, плюс `counts`.
* Пара — «архетип стиля × блюдо каталога» (архетип напитка — `style.archetype` из `data/drinks.json`): два лагера одного
  стиля копят оценки вместе.
* Берём только опубликованные отзывы; своё блюдо и отзывы «ел другое блюдо» — нет.
* Порог: **≥ 8 отзывов от ≥ 5 разных гостей**. Средняя — **по гостям, а не по отзывам**: сначала средняя каждой
  сессии, потом среднее сессий (гость из заведения ×1.5) — один злой гость, оценивший четыре лагера, остаётся одним голосом.
* Средняя ≥ 4.2 → `expect: "good"`, ≤ 2.4 → `"bad"`, между — пропуск: гости не уверены, это не эталон.
* Нет подходящих пар — файл всё равно пишется с пустым списком. Никаких выдуманных записей.

**Почему сигнал слабый.** Гости оценивают удовольствие, а не совместимость по правилам; оценивают те, кто любит
нажимать кнопки; на оценку влияют подача, температура, настроение и компания. Поэтому гостевые пары идут только
в train, а их вес задаёт калибратор (`scripts/calibrate_v2.py`, `ORIGIN_WEIGHT` по полю `origin`). Предлагаем
`"guests": 0.25` — вчетверо меньше литературы и вдвое меньше кураторских пар команды. Сейчас калибратор читает только
`data/test_pairs.json`: `guest_pairs.json` нужно подмешать к парам там же (это делает владелец калибратора).

## API

| Метод и путь | Доступ | Что делает |
|---|---|---|
| `POST /api/v2/reviews/` | все | создать или обновить свой отзыв; тело: `drink_id`, `dish_id` (`custom` + `dish_name`), `rating` 1–5, `chips[]`, `text`, `helpful`, `locale`, `session`, `venue`, `table`, `score_shown`, `ctx{}`. Ответ 201/200: `review` (без хешей), `applied_prefs {delta, notes}`, `aggregate`, `status`, `pending`, `message` (+ `session`, если клиент его не прислал) |
| `GET /api/v2/reviews/pair/?drink=&dish=[&dish_name=][&limit=]` | все | сводка пары + последние опубликованные отзывы с текстом |
| `GET /api/v2/reviews/drink/<id>/[?limit=]` | все | сводка напитка по всем блюдам, частые метки, блюда, последние тексты |
| `GET /api/cabinet/reviews/[?days=]` | Bearer-токен кабинета | отзывы своего заведения, пары, метки, «на доработку» |
| `GET /api/v2/reviews/moderation/[?status=queue\|pending\|spam\|hidden\|published\|all&limit=&offset=]` | сомелье | очередь модерации (по умолчанию pending + spam) |
| `POST /api/v2/reviews/<uuid>/moderate/` `{status}` | сомелье | решение модератора |

Ошибки: 400 `{detail, field}` — что не так и в каком поле; 401/403 — как у `/api/admin/*` и кабинета; 429 — лимит,
`Retry-After` в заголовке и `retry_after` в теле.

## Лимиты

| Кто | За минуту | За час |
|---|---|---|
| одна сессия гостя | 5 записей | 30 |
| один IP | 10 | 60 |

IP вдвое щедрее: за одним адресом бывает Wi-Fi бара или мобильный NAT оператора. Правка своего отзыва не занимает
новое место, но не чаще раза в 3 с. Считается по базе (строки за окно), внешний кэш не нужен.

## Фронтенд

| Файл | Что это |
|---|---|
| `core/reviews.service.ts` | клиент API, словарь меток (зеркало бэкенда), расчёт поправки в режиме без сервера |
| `core/guest-prefs.service.ts` | личный профиль: сигнал в localStorage (`ft.guest.prefs.v1`), `applyDelta()`, `ctx()` для движка, «что мы учли» |
| `ui/pair-review.component.ts` | `<ft-pair-review [drinkId] [dishId] [dishName] [score] [ctx] [venueSlug] [table]>` — «Как вам пара?» |
| `ui/review-summary.component.ts` | `<ft-review-summary [drinkId] [dishId]>` — сводка пары или напитка, последние тексты с метками ИИ |
| `pages/cabinet/cabinet-reviews.component.ts` | `<ft-cabinet-reviews />` — блок «Отзывы гостей» для кабинета |

Звёзды — нативная группа радиокнопок (стрелки, Tab и скринридер работают без своего кода), метки — кнопки
с `aria-pressed`, у текста — счётчик. Подписи — ключи `review.*` и `prefs.*` в `core/i18n/{ru,kk,en}.ts`;
кабинет, как и весь кабинет, на русском.

**Без сервера (демо на Vercel, `API_URL` пуст)** отзыв сохраняется только в браузере гостя
(`ft.reviews.device-only.v1`), нигде не публикуется, и виджет так и пишет: «Сохранено только на этом устройстве».
Сводки в этом режиме честно пустые — «Оценок пока нет». Профиль подстраивается так же, как с сервером.
С сервером копия своего отзыва лежит в `ft.reviews.mine.v1` — чтобы показать «Ваша оценка» и дать её изменить.

## Настройки окружения

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `ANTHROPIC_API_KEY` | — | включает ИИ-разбор текстов; без ключа тексты ждут модератора |
| `FT_REVIEWS_AI` | вкл. | `0` — выключить ИИ-разбор при заданном ключе |
| `FT_REVIEWS_AI_TIMEOUT` | 8 | таймаут разбора, секунды (1–30) |
| `FT_PROXY_HOPS` | 0 | за обратным прокси: сколько последних адресов `X-Forwarded-For` дописали наши прокси. **Без этой настройки за прокси все гости выглядят одним IP** и упрутся в общий лимит — на проде за балансировщиком выставить `1` |
| `FT_ADMIN_TOKEN` | — | доступ к модерации (как у остального служебного API) |

## Тесты

```
cd backend && .venv/bin/python manage.py test api.tests.test_reviews
```

Сети не нужно: ключ API убирается из окружения, клиент Anthropic подменён заглушкой; отдельный тест прогоняет
настоящий SDK через подменный транспорт — проверяет заголовок beta и тело запроса. Покрыто: создание и правка,
400 на кривые поля, лимиты, математика сводки (сжатие, n < 3, вес ×1.5, расхождение), поправки профиля, эвристики,
ИИ-разбор (успех, отказ, битый JSON, таймаут, попытка инъекции в тексте), доступ к модерации (401/403),
