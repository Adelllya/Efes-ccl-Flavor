# ИИ-сомелье Flavor Tree v2

Два режима для гостя:

- **«Блюдо»** — вопрос текстом («что взять к мантам, не люблю горькое») или фото блюда (AI Food Scanner, приоритет №1 по CustDev, `research.md` §8.1). Ответ — напитки из движка подбора v2: пиво, безалкогольное, сидр, вино, коктейли, крепкое, квас, кумыс и т. д.
- **«Напиток»** (новое) — название, строка из меню или фото этикетки. Ответ — что это за напиток (из каталога или честная оценка по этикетке) и к каким блюдам он подойдёт.

## Принцип: ИИ переводит, движок решает

```
гость (текст / фото блюда / фото этикетки)
   │
   ▼  Claude (claude-opus-5, строгий JSON по схеме; всё, что вернула модель, сервер проверяет заново)
┌──────────────────────────────────────────────────────────────────────────────────┐
│ «блюдо»:   kind dish | drink | clarify | chat                                      │
│            dish: matched_slug (id из dishes_v2) | null, taste, weight, fat, cook,   │
│                  protein, sauce, acid, dessert, heat 0..1, tags [{tag, weight}],    │
│                  cuisine[], confidence                                              │
│            occasion (meal|aperitif|dessert|hot|evening|party|gourmet|non_alcoholic) │
│            bitter_pref −1..1, heat_lover                                            │
│ «напиток»: kind drink | clarify                                                     │
│            drink: matched_drink_id (id из drinks.json) | null, name, producer,      │
│                   category, archetype (id из style_priors_v2), read_from_label      │
│                   {abv, ibu, sugar_category, other[]}, adjustments ±0.15,           │
│                   aroma_tags, confidence, questions[]                               │
│            with_dish: описание блюда, если гость его назвал                          │
└──────────────────────────────────────────────────────────────────────────────────┘
   │
   ▼  Движок подбора v2 (детерминированный, паритет Python ↔ TS, docs/PAIRING_ENGINE_V2.md)
   «блюдо»:   recommend — топ-3 напитка (только из карты заведения, если гость в баре) + лучший из портфеля Efes
   «напиток»: reverse — 5 лучших блюд каталога + оценка пары с названным блюдом (score_pair)
   │
   ▼  Claude (объяснение словами сомелье, 2–4 предложения, без markdown; на языке гостя — ru / kk / en)
ответ гостю + кнопка «Заказать» + ссылки «Полный разбор» (/pair/:dish) и «Карточка напитка» (/drinks/:id)
```

Почему так, а не «спросить у модели, что выпить»:
- **Объяснимость.** Оценка раскладывается по правилам движка (R1–R20), у каждой причины — уровень доказательности A–D.
- **Контроль ассортимента.** Модель физически не может посоветовать напиток, которого нет в карте: список напитков заведения передаётся движку, а не модели.
- **Стабильность.** Одинаковое блюдо → одинаковые напитки. Модель только распознаёт и объясняет.
- **Честность.** Оценки не зависят от бренда; политика Efes (ниже) — правило продукта в движке, не решение модели.

## Где работает

| Где | Файлы | Когда используется |
|---|---|---|
| Vercel Function | `frontend/api/ai.ts` → `frontend/api/_lib/{sommelier,analysis,catalog,prompts}.ts` | Демо без Django. Импортирует **тот же TS-движок v2** (`src/app/engine/pairing-engine-v2.ts`, `custom-dish-v2.ts`) и копии данных из `frontend/api/_data`. |
| Django | `backend/api/ai.py` (+ `backend/api/dish_autofill.py`) → `POST /api/ai/` | Прод с бэкендом: данные — `dataset_v2.get_dataset()` (data/*.json, параметры с калибровкой), цены и стоп-лист — из БД по `venue.slug`. |
| SPA | `core/ai.service.ts`, `ui/sommelier-chat.component.ts`, `pages/scan/scan.page.ts` | Сканер с переключателем «Блюдо / Напиток» (`/scan`, `/scan?mode=drink`), чат с кнопкой «Разобрать напиток». |

Адрес выбирается в `core/config.ts`: `window.FT_AI_URL` → иначе `API_URL + '/ai/'` → иначе `/api/ai` (Vercel).

**Данные для Vercel.** Функция не видит файлы выше `frontend/`, поэтому `node scripts/sync-data.mjs` копирует в `frontend/api/_data`: `dishes_v2.json`, `drinks_v2_spa.json`, `engine_v2_spa.json`, `style_priors_v2.json`. Копии коммитятся вместе с кодом: `npm run build` этот скрипт сам **не** вызывает. После пересборки каталога (`scripts/build_catalog_v2.py`, `scripts/build_spa_data_v2.py`) — запустить синхронизацию. Копии данных v1 (`brands.json`, `dishes.json` и др.) функции больше не нужны и из `api/_data` удалены.

## Контракт

`POST /api/ai` (Vercel) или `POST /api/ai/` (Django), JSON.

### Запрос

```jsonc
// режим «блюдо», текст
{ "mode": "ask", "messages": [{"role": "user", "content": "что к казы в жару?"}],
  "venue": { "slug": "efes-beer-garden-almaty", "name": "…", "beers": ["13-region", "kozel"],
             "prices": {"13-region": 1750}, "volumes": {"13-region": "0.5 л"}, "currency": "₸" },
  "occasion": null, "bitter_pref": 0, "sweet_pref": 0, "heat_lover": false, "harsh_tol": null,
  "non_alcoholic": false, "dna": null, "locale": "kk" }

// режим «блюдо», фото
{ "mode": "vision", "image": {"media_type": "image/jpeg", "data": "<base64>"}, "messages": [], "locale": "en" }

// режим «напиток»: название / строка меню и/или фото этикетки
{ "mode": "drink", "messages": [{"role": "user", "content": "Blanche de Namur 4.5%, к шашлыку"}] }
{ "mode": "drink", "image": {"media_type": "image/jpeg", "data": "<base64>"}, "messages": [] }
```

- `venue.beers` — сорта заведения: slug брендов v1 (как в карте `VenueMenuItem.ref_slug`) или id напитков v2. Сервер переводит slug v1 в id v2 через `legacy_brand_id` (как `PairingV2Service.venueDrinkIds`); цены и объёмы ищутся по id v2, затем по slug v1. Пустой список или нет поля — без фильтра. В Django, если `beers` не передан, карта берётся из БД по `venue.slug` (позиции `kind=BEER`, стоп-лист учтён).
- `occasion` — повод v2; неизвестное значение отбрасывается. Если гость назвал повод словами, модель его услышит, но выбранный в интерфейсе повод важнее.
- `bitter_pref`, `sweet_pref` (−1..1), `heat_lover`, `harsh_tol` (`sensitive | median | tolerant`), `non_alcoholic` — личные настройки движка (R17, V7). Значение из запроса важнее того, что модель услышала в словах гостя.
- `dna` — Flavor DNA **в осях v2** (`R17.dna.axes`). Вектор v1 (оси `malt_sweet`, `hop_aroma`…) отбрасывается: у v1 другая шкала (`alcohol` v1 ≠ ABV/40), он исказил бы оценки. SPA пока DNA не отправляет.
- `locale` — `"ru"` | `"kk"` | `"en"`; нет поля или другое значение → `"ru"`.

### Ответ

Все ключи есть в любом успешном ответе (пустые — `null` / `[]`):

```jsonc
{ "ok": true, "engine": "v2", "kind": "picks",            // picks | clarify | chat | drink
  "reply": "К казы берите Efes Pilsener — …",
  "dish": { "name": "Казы", "slug": "kazy", "emoji": "🥩", "confidence": 0.92,
            "vector": { "salt": 0.8, "fat": 0.85, … },      // 16 осей блюда, которые ушли в движок
            "spec": { "taste": "SALTY", "weight": "HEAVY", "fat": "HIGH", "cook": "cured", "protein": "horse",
                      "sauce": "none", "acid": "none", "dessert": false, "heat": 0, "tags": {"cured": 0.7}, "cuisine": ["kazakh"] } },
  "picks": [{ "drink_id": "efes-pilsener", "beer_id": "efes-pilsener",   // beer_id — старое имя поля, = drink_id
              "name": "Efes Pilsener", "category": "beer", "category_label": "Пиво", "style": "Международный светлый лагер",
              "archetype": "pale_lager_intl", "abv": 5, "score": 78, "band": "excellent", "band_label": "Отличное сочетание",
              "match_type": "cut", "match_label": "Очищает", "secondary_type": null,
              "why": "Пузырьки смывают жир с языка — каждый глоток как первый (Oliver)",
              "reasons": [{ "text": "…", "evidence": "B" }], "warnings": [{ "text": "…", "evidence": "C" }],
              "classic": false, "efes_partner": true, "price": 1750, "volume": "0.5 л", "image": "img/beers/efes-pilsener.webp" }],
  "best_partner": null,          // лучший напиток Efes с честной оценкой — только если его нет среди picks
  "drink": null, "dishes": [], "pair": null, "questions": [],
  "route": "/pair/kazy?occasion=hot", "occasion": "hot", "locale": "ru",
  "usage": { "input": 2310, "output": 260, "cache_read": 8900, "cache_write": 0, "calls": 2, "fallbacks": 0 } }
```

- `why` — одна строка «почему»: сильнейший механизм пары (cut / complement / contrast / bridge, как тип пары у движка), иначе первая причина.
- `reasons` — до трёх сильнейших плюсов, `warnings` — вето и минусы; `evidence`: **A** — измерено в лабораторных экспериментах, **B** — показано на дегустационных панелях, **C** — мнение сомелье и учебников, **D** — гипотеза.
- `route` для своего блюда — `/pair/custom?name=…&taste=…&weight=…&fat=…&cooking=<v1>&heat=0..100&cook=…&protein=…&sauce=…&acid=…&dessert=0|1&tags=onion:0.50,…`. Параметры мастера v1 (`cooking`, `taste`…) страница подбора уже понимает; поля v2 (`cook`, `protein`, `sauce`, `acid`, `dessert`, `tags`) добавлены, чтобы страница считала своё блюдо так же, как ИИ.

Ответ режима «напиток»:

```jsonc
{ "ok": true, "engine": "v2", "kind": "drink", "reply": "Это бельгийский витбир — его профиль оценка по этикетке…",
  "drink": { "id": null, "name": "Blanche de Namur", "producer": "Brasserie du Bocq", "category": "beer", "category_label": "Пиво",
             "style": "Бельгийское белое (витбир)", "archetype": "witbier", "family": "WHEAT", "abv": 4.5, "ibu": null,
             "sensory": { "sweet": 0.2, "acid": 0.5, … }, "aroma_tags": { "citrus": 0.8, … },
             "serving": { "temp_min_c": 3, "temp_max_c": 7, "glass": "бокал для пшеничного пива" },
             "estimated": true, "vector_source": "ai_estimate", "vector_confidence": 0.32, "recognition_confidence": 0.8,
             "what_was_read": ["Крепость 4.5 %", "«пшеничное»"],
             "what_was_assumed": ["Стиль «Бельгийское белое (витбир)» — определил ИИ", "Горечь, сладость, кислотность, тело, газация — типичные для стиля", …],
             "vector_notes": ["Стиль … определил ИИ по названию; уверенность распознавания 80 %.", "ABV 4.5 % — прочитано на этикетке → alcohol 0.11.", …],
             "efes_relation": "none", "efes_partner": false, "image": null },
  "dishes": [{ "dish_id": "mussels-steamed", "name": "Мидии на пару", "emoji": "🦪", "score": 89, "band": "ideal", "band_label": "…",
               "match_type": "cut", "match_label": "Очищает", "secondary_type": null, "why": "…", "reasons": […], "warnings": […],
               "classic": true, "route": "/pair/mussels-steamed" }],
  "pair": { "dish_id": "shashlyk", …, "route": "/pair/shashlyk" },   // если гость назвал блюдо
  "questions": ["Оно с кориандром или без?"],                         // уточнения от модели (не больше двух)
  "route": null,                                                     // у каталожного напитка — "/drinks/<id>"
  "picks": [], "best_partner": null, "dish": null, "occasion": null, "locale": "ru", "usage": {…} }
```

`kind: "clarify"` — модель задала уточняющий вопрос (в `reply`), `kind: "chat"` — ответ на общий вопрос (что такое лагер, температура подачи). Если в режиме «блюдо» гость спрашивает, что поесть под конкретный напиток («что поесть под Kozel?»), модель отвечает `kind: "drink"`, и сервер тем же вопросом запускает режим «напиток» (три вызова вместо двух).

Ошибки: `{ok: false, error}` со статусами 400 (нет режима, пустой вопрос, не тот формат фото) / 413 (фото больше лимита) / 429 / 502 (ИИ ответил неразборчиво или нет связи) / 503 («ИИ не настроен»). Тексты ошибок пока по-русски.

## Режим «напиток»: откуда берётся профиль

1. Модель сопоставляет напиток с каталогом (`matched_drink_id` — только если совпадают бренд и сорт; похожий стиль другого бренда — не совпадение). Сервер принимает id, только если он есть в каталоге.
2. **Нашёлся в каталоге** → берётся каталожная запись целиком (`estimated: false`). В «прочитано» — то, что видно на этикетке; если крепость на этикетке расходится с каталогом на 0.3 % и больше, гость это видит («В каталоге крепость 4.5 % — для подбора взят каталог»). Подробные заметки о профиле — на карточке напитка.
3. **Не нашёлся** → профиль собирается на сервере (модель чисел профиля не задаёт):
   - приор стиля из `data/style_priors_v2.json` (132 архетипа с якорями BJCP / регламентов); стиль не из списка или другой категории → типичный стиль категории, это пишется в заметки;
   - якоря с этикетки: ABV → `alcohol = ABV/40`; IBU → `bitter = clamp((IBU−8)/62)` (только пиво и безалкогольное пиво); сахар вина, игристого, креплёного, сидра → `sweet` по шкале г/л ENGINE_V2_SPEC §2.1 (середина диапазона категории: полусладкое ≈ 30 г/л → 0.45; у игристого dry ≈ 24.5 г/л → 0.39; сидр — шкала BJCP: полусладкий 0.55);
   - поправки ИИ — не больше шести, каждая зажата в ±0.15 и только к осям, которые **не** взяты с этикетки (поправка к горечи при прочитанном IBU отбрасывается);
   - ароматы стиля + ароматы, которые модель увидела или знает для напитка (только из общего словаря тегов);
   - `vector_source: "ai_estimate"`, `vector_confidence = min(0.45, (0.25 + 0.10 за ABV с этикетки + 0.10 за IBU или сахар с этикетки) × (0.6 + 0.4·уверенность распознавания))`;
   - каждый шаг — строка в `vector_notes`, как в `data/drinks.json`;
   - `efes_relation` незнакомого напитка — всегда `none`: бренд, которого нет в каталоге, портфелю не приписывается.
4. Движок v2 `reverse` → 5 лучших блюд каталога; если гость назвал блюдо — `score_pair` с ним (блюдо из каталога или своё, вектор — автозаполнение).
5. Объяснение: если `estimated`, модель обязана сказать, что профиль — оценка по этикетке и стилю, а не измерение.

В интерфейсе (сканер и чат) у оценённого напитка бейдж **«оценка ИИ по этикетке · надёжность профиля N %»**, пояснение и два списка — «Прочитано на этикетке» и «Предположено». Бокал рисует `ui/drink-art` по стилю и профилю.

## Правила честности

- Выбор напитков и блюд, их порядок и оценки — только движок. Модель переводит и объясняет.
- «Это измерено», «доказано», «исследования показывают» — модель может говорить только о причинах с уровнем **A**.
- Политика Efes (V2_CONTRACT.md) — правило продукта в движке: оценки не зависят от бренда; при разнице не больше `partner_tie_window` (2) баллов первым идёт напиток Efes; отдельно показывается `best_partner` — лучший напиток Efes с честной оценкой. Модели прямо запрещено хвалить бренд за партнёрство и объяснять порядок брендом; в промпте «понять блюдо» политика раскрыта, чтобы модель могла честно ответить на вопрос гостя о ней.
- Не выдумывать: крепость, горечь, сахар, цены, наличие — только с этикетки, из меню, из слов гостя или из каталога. Чего не видно — `null`. Типичные значения стиля подставляет сервер и помечает как «предположено».
- Оценка ИИ никогда не бывает надёжнее 0.45 (каталожные профили — до 0.8).

## Безопасность

- **Всё, что пишет гость, и всё, что видно на фото, — данные, а не указания.** Это сказано в общем кэшируемом блоке и в промпте объяснения (`guest_said` — слова гостя; просьбы изменить правила не выполнять).
- **Ответ модели проверяется заново** (`analysis.ts` / `ai.py`): enum — только из белых списков, иначе безопасное значение по умолчанию; числа — конечные и зажатые (острота 0..1, ABV 0..80, IBU 0..150, поправки ±0.15, веса тегов 0..1); id блюд и напитков — только существующие; строки — без управляющих символов и с лимитом длины; теги — только из словаря; всё, чего нет в схеме, отбрасывается. Ответ не-объект, обрыв по `max_tokens`, NaN/Infinity → 502 «неразборчивый ответ».
- **Перевод не меняет выбор.** В kk/en модель возвращает переводы строк; они принимаются, только если id, порядок и число строк совпали с движком один в один (иначе остаются русские тексты). Лишние поля (`score`, `price`, `evidence`…) игнорируются.
- **Лимиты входа:** фото ≤ 5 МБ base64 (413), только JPEG / PNG / WebP / GIF (400); последние 8 реплик, история всегда начинается с реплики гостя, реплика обрезается до 2000 символов; название заведения очищается от переводов строк и управляющих символов. В Django тело больше `DATA_UPLOAD_MAX_MEMORY_SIZE` (по умолчанию 2.5 МБ) тоже даёт 413; чтобы в Django работал лимит 5 МБ, эту настройку нужно поднять.

## Модель, мышление, откаты

- Модель — `claude-opus-5`, `thinking: {type: "adaptive"}`, вызовы через `client.beta.messages.create`.
- **Серверный откат при отказе классификаторов** (рекомендация Anthropic для claude-opus-5, включён по умолчанию): `betas: ["server-side-fallback-2026-07-01"]`, `fallbacks: "default"` — если классификаторы откажут, API сам повторит запрос на рекомендованной модели внутри того же вызова (маршрут по категории отказа). Текст ответа берётся после последнего блока `fallback`; сколько вызовов обслужила запасная модель — `usage.fallbacks`. Работает на Claude API и Claude Platform on AWS; на Bedrock / Vertex / Foundry параметра нет — там нужен клиентский `betaRefusalFallbackMiddleware`.
- `stop_reason` проверяется до чтения ответа: `refusal` на первой фазе → мягкая готовая фраза (`kind: "chat"`); `refusal` или обрыв на объяснении → остаётся фраза первой фазы и русские тексты движка, запрос не падает.
- effort: распознавание по тексту — `low`, по фото — `medium` (этикетку и тарелку читать сложнее); объяснение — `low`. `max_tokens` (с учётом мышления): распознавание 4096, объяснение 2048 (ru) / 4096 (kk/en).
- Промпты не просят модель «перепроверять себя» (для Opus 5 это лишняя работа) и прямо ограничивают объяснение 2–4 предложениями.

## Язык гостя (ru / kk / en)

| Поле | ru | kk / en |
|---|---|---|
| `reply`, `questions` | модель | модель на языке гостя |
| `why`, `reasons[].text`, `warnings[].text` у напитков и блюд, `what_was_read`, `what_was_assumed` | русский текст движка / сервера | перевод, полученный тем же вызовом «объяснение» (строгий JSON) |
| `match_label`, `band_label`, `category_label` | статичные подписи | статичные карты в коде; модель не участвует |
| готовые фразы (отказ, пустое уточнение, «в карте нет подходящего напитка») | статичные строки | статичные строки |
| выбор, порядок, оценки, `evidence`, цены, маршруты, `vector_notes`, `style`, названия | движок / каталог | не переводятся |

**Перевод.** Для kk/en в brief объяснения добавляется `translate: {items: [{id, why, reasons, warnings}], notes: [...]}`, ответ — строгий JSON `{reply, items, notes}`. `items` принимаются целиком, только если совпали id, порядок и число строк; `notes` — если совпало число строк. Любое расхождение, оборванный или неразборчивый JSON, отказ → остаются русские тексты, запрос не падает (если `reply` годен, он используется).

**Казахский** — естественный современный казахский кириллицей, коротко, без кальки с русского; названия блюд можно оставлять, как их написал гость, названия напитков не переводятся.

## Кэш промпта

Кэш Anthropic — совпадение префикса байт-в-байт до блока с `cache_control`. Блоки `system`:

| Вызов | Блок 1 (кэш) | Блок 2 (кэш) | Последний блок (без кэша) |
|---|---|---|---|
| понять блюдо | общий: роль, безопасность, политика Efes, как описывать блюдо, 114 блюд, 132 стиля, словарь тегов (~23 тыс. символов) | правила «понять блюдо» | язык гостя (kk/en) |
| разобрать напиток | тот же общий блок | каталог 412 напитков + правила (~44 тыс. символов) | язык гостя |
| объяснить | правила объяснения (~1.8 тыс. символов) | — | язык гостя |

Общий блок один на оба режима и на все языки: гость на казахском попадает в кэш, прогретый гостем на русском, а разбор напитка — в кэш, прогретый подбором к блюду. Указание языка идёт system-блоком, а не текстом в реплике гостя, чтобы гость не мог его подменить. Оговорки: разные effort (текст / фото) и разные схемы вывода могут вести отдельные записи кэша; промпт объяснения (~1.8 тыс. символов, порядка 500–700 токенов) — около минимального кэшируемого префикса claude-opus-5 (512 токенов), кэшируется ли он, видно только по `usage.cache_read` в ответе (`usage.input` — только некэшированный остаток).

## Стоимость (оценка, не замер)

Цены claude-opus-5: вход $5 / млн токенов, выход $25; запись в кэш ×1.25, чтение из кэша ×0.1.
- Подбор к блюду текстом: общий блок + правила ≈ 8–10 тыс. токенов (при тёплом кэше ≈ $0.005), реплика и brief — сотни токенов, выход с мышлением на low ≈ 300–1000 токенов на вызов. Итого ≈ $0.02–0.04 за ответ; первый запрос после 5 минут тишины дороже на запись кэша (≈ $0.06).
- Фото блюда: + ~1–1.5 тыс. токенов картинки и больше мышления (effort medium).
- Разбор напитка: общий блок + каталог напитков ≈ 22–28 тыс. токенов в кэше (чтение ≈ $0.013, холодная запись ≈ $0.16), остальное как у подбора.
- kk/en: объяснение длиннее (перевод 10–25 строк) — выходных токенов больше.
Реальные числа — в `usage` ответа: `cache_read` должен быть больше нуля со второго запроса подряд.

## Ограничения и что дальше

- Страница `/pair/custom` пока читает только параметры мастера v1; поля v2 из маршрута (`cook`, `protein`, `sauce`, `acid`, `dessert`, `tags`) нужно подхватить в `pages/pair/pair-results.page.ts`, иначе «полный разбор» своего блюда считается грубее, чем у ИИ.
- Названия стилей (`style`) и категории блюд — по-русски на всех языках; kk/en-имена есть только у блюд v1.
- Flavor DNA гостя в v2 не передаётся, пока DNA не посчитана в осях v2.
- Голосовой ввод, мультиблюдо на фото, распознавание всей карты напитков заведения по фото меню — следующие шаги.
