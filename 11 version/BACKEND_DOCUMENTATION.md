## 1. Что делает бэкенд

Идея продукта: любое пиво можно разложить на «вкусовую пирамиду» из трёх слоёв - что чувствуешь в первые секунды (TOP), что составляет тело вкуса (HEART) и что остаётся в послевкусии (BASE). Бэкенд хранит эти пирамиды для сортов из портфеля Efes Kazakhstan и отдаёт их фронтенду.

Сейчас он умеет четыре вещи:

- каталог пива с фильтрами и карточкой каждого сорта (пирамида, рекомендации по подаче, фото);
- справочник вкусовых нот, в том числе обратный поиск «в каких сортах есть эта нота»;
- фуд-пейринг: 50 блюд шести кухонь и 51 пара «пиво + блюдо» с оценкой и объяснением, почему они сочетаются;
- рабочее место сомелье: заполнение пирамиды, температуры подачи, загрузка фото.

Фронтенд на Angular (`frontend/`) ходит на `http://127.0.0.1:8000/api`.

## 2. Стек

- Python 3.9+
- Django 4.2 и Django REST Framework 3.14+
- PostgreSQL (драйвер `psycopg2-binary`)
- `django-cors-headers` - чтобы Angular на порту 4200 мог обращаться к API
- `Pillow` - для загрузки изображений

Полный список зависимостей лежит в `backend/requirements.txt`.

## 4. Модели данных

У всех моделей первичный ключ - UUID, а не числовой id. По такому адресу нельзя перебирать записи подряд, и данные проще переносить между базами.

Как модели связаны между собой:

```
FlavorNote ──┐
             ├── FlavorProfile ──── Brand ──── ServingRecommendation (1:1)
             │   (слой, интенсивность)   │
             │                           └──── FoodPairing ──── Dish
             │
Venue ──── QRCode ──── AnonymousSession

Course и TeamMember ни с чем не связаны, это контент для лендинга.
```

### FlavorNote - вкусовая нота

Справочник дескрипторов. Названия и технические термины взяты из лексикона FlavorActiV (Beer Flavour Wheel).

| Поле | Тип | Что хранит |
|------|-----|-----------|
| name | CharField(100) | название по-русски: «Хмелевой аромат», «Карамель» |
| technical_term | CharField(100) | термин из лексикона: `Hop Aroma`, `Caramel / Maltol` |
| wheel_code | CharField(10) | код на колесе вкусов, если есть |
| category | CharField | слой пирамиды: `TOP`, `HEART` или `BASE` |
| description | TextField | как эта нота ощущается |
| icon | CharField(10) | эмодзи для интерфейса |
| reference_material | CharField(200) | эталон для тренировки: с чем сравнивать |
| is_off_flavour | Boolean | нота-дефект (например, масляный привкус) |
| sort_order | Integer | порядок в списке |

Слои:

- `TOP` - верхние ноты, первые 0-3 секунды: аромат, свежесть, карбонизация;
- `HEART` - ноты сердца, 3-15 секунд: солод, карамель, зерно;
- `BASE` - базовые ноты, 15+ секунд: горечь и послевкусие.

### Brand - сорт пива

Главная сущность каталога.

| Поле | Тип | Что хранит |
|------|-----|-----------|
| name | CharField(200) | название |
| brand_owner | CharField(100) | владелец марки |
| style | CharField(100) | стиль: Lager, Pilsner, Rice Beer |
| abv | Float, может быть пустым | крепость в процентах |
| density | CharField(100) | плотность |
| fermentation_type | CharField(100) | тип брожения |
| packaging_type | CharField | `BOTTLE`, `CAN` или `DRAFT` |
| is_horeca_only | Boolean | продаётся только в заведениях |
| description | TextField | описание |
| image | ImageField | фото, файл сохраняется в `media/brands/` |
| is_active | Boolean | показывать ли в каталоге |
| created_at | DateTime | когда добавили |

Одно правило зашито прямо в `save()`: если упаковка `DRAFT`, то `is_horeca_only` автоматически становится `True`. Разливное пиво в магазине не купишь, и мы не хотим зависеть от того, вспомнит ли человек поставить галочку.

Крепость у многих сортов пока пустая: проверенных цифр по ним у нас нет, поэтому поле разрешено оставлять незаполненным.

### FlavorProfile - нота в пирамиде конкретного сорта

Связка «сорт - нота» с дополнительными данными. Именно из этих записей собирается пирамида.

| Поле | Тип | Что хранит |
|------|-----|-----------|
| brand | FK → Brand | сорт |
| flavor_note | FK → FlavorNote | нота |
| layer | CharField | в каком слое стоит: `TOP`, `HEART`, `BASE` |
| intensity | Integer | насколько выражена, от 1 до 10 |
| sommelier_note | TextField | комментарий сомелье |
| sommelier_name | CharField(150) | кто оценивал |
| updated_at | DateTime | когда меняли |

Пара (brand, flavor_note) уникальна - одну ноту нельзя добавить сорту дважды.

В первой версии у пива было три отдельных поля many-to-many, по одному на слой. От этого мы отказались: в такой схеме некуда записать интенсивность и комментарий, а без интенсивности пирамида превращается в простой список тегов.

### ServingRecommendation - как подавать

Одна запись на сорт (OneToOne): `serving_temp_min`, `serving_temp_max` в градусах Цельсия, `glass_type` (тип бокала) и `seasonality`.

### Dish - блюдо

| Поле | Тип | Что хранит |
|------|-----|-----------|
| name | CharField(200) | название |
| cuisine | CharField | `KZ`, `ITALIAN`, `JAPANESE`, `AMERICAN`, `MEXICAN`, `GERMAN`, `OTHER` |
| category | CharField(100) | «Мясное», «Десерт», «Закуска» - свободный текст |
| dominant_taste | CharField | `SALTY`, `SWEET`, `SOUR`, `BITTER`, `UMAMI`, `SPICY`, `MIXED` |
| weight | CharField | `LIGHT`, `MEDIUM`, `HEAVY` |
| fat_level | CharField | `LOW`, `MEDIUM`, `HIGH` |
| cooking_method | CharField | `FRIED`, `GRILLED`, `BAKED`, `BOILED`, `STEAMED`, `RAW`, `CURED`, `FERMENTED`, `OTHER` |
| description | TextField | описание |
| image | URLField | ссылка на фото |

Вкус, вес и жирность здесь не для красоты: это входные данные для будущего автоматического подбора пива. Подробнее про блюда - в [Flavor_Tree_Dishes_50.md](Flavor_Tree_Dishes_50.md).

### FoodPairing - пара «пиво + блюдо»

| Поле | Тип | Что хранит |
|------|-----|-----------|
| brand | FK → Brand | сорт |
| dish | FK → Dish | блюдо |
| compatibility_score | Integer | оценка от 1 до 5 |
| pairing_type | CharField | `COMPLEMENT`, `CONTRAST`, `CLEANSE`, `BRIDGE` |
| explanation | TextField | почему это работает |

Типы пар:

- `COMPLEMENT` - похожие вкусы усиливают друг друга;
- `CONTRAST` - противоположности уравновешивают (жирное и горькое);
- `CLEANSE` - пиво освежает после тяжёлого или острого;
- `BRIDGE` - у пива и блюда есть одна общая нота, например дым или карамель.

Сама матрица - в [Flavor_Tree_Food_Pairings.md](Flavor_Tree_Food_Pairings.md).

### Course и TeamMember

Контент для лендинга. `Course` - четыре уровня Школы пивных сомелье (Новичок, Исследователь, Знаток, Сомелье) с полями `level`, `title`, `description`, `color`, `required_score`. `TeamMember` - `name`, `role`, `bio`, `avatar`.

### Venue, QRCode, AnonymousSession

Задел под сценарий «гость сканирует QR-код на столике в баре». `Venue` - заведение, `QRCode` - код, привязанный к столику (с токеном и счётчиком сканирований), `AnonymousSession` - сессия гостя без регистрации: пройденные уровни, баллы и предпочтения в JSON.

Таблицы созданы и доступны в Django-админке, но эндпоинтов в API для них ещё нет.

## 5. API

Все адреса начинаются с `/api/`. Формат - JSON. Чтение каталога открыто всем, запись требует входа и роли (см. [раздел 12](#12-версия-11-что-добавилось-на-сервере)).

Списки отдаются постранично, по 20 записей:

```json
{ "count": 50, "next": "http://127.0.0.1:8000/api/dishes/?page=2", "previous": null, "results": [] }
```

Следующая страница - параметр `?page=2`.

### Каталог пива

| Метод | Адрес | Что делает |
|-------|-------|-----------|
| GET | `/api/brands/` | список сортов |
| GET | `/api/brands/{id}/` | карточка сорта вместе с пирамидой |
| GET | `/api/brands/{id}/pyramid/` | только пирамида |
| POST | `/api/brands/` | добавить сорт |
| PUT, PATCH | `/api/brands/{id}/` | изменить |
| DELETE | `/api/brands/{id}/` | удалить вместе с профилями, подачей и парами |
| POST | `/api/brands/{id}/upload-image/` | загрузить фото, `multipart/form-data`, поле `image` или `file` |

Параметры списка:

| Параметр | Пример | Как работает |
|----------|--------|--------------|
| `q` | `?q=efes` | поиск по названию, регистр не важен |
| `style` | `?style=lager` | по вхождению в стиль |
| `packaging_type` | `?packaging_type=draft` | `BOTTLE`, `CAN`, `DRAFT` |
| `is_horeca_only` | `?is_horeca_only=true` | только для заведений |
| `is_active` | `?is_active=true` | только те, что в наличии |
| `ordering` | `?ordering=-abv` | `name`, `abv`, `style`, `created_at`; минус впереди - по убыванию |

В списке у каждого сорта есть блок `profile`: сколько нот в каждом слое и статус пирамиды - `empty`, `partial` или `complete`. Полной пирамида считается, когда заполнены все три слоя. По этому статусу фронт показывает сомелье, какие сорта ещё не разобраны.

Через `PATCH /api/brands/{id}/` можно заодно передать вложенный объект `serving_recommendation` - он создастся или обновится.

### Вкусовые ноты

| Метод | Адрес | Что делает |
|-------|-------|-----------|
| GET | `/api/flavor-notes/` | справочник; фильтры `?category=TOP` и `?off_flavour=true` |
| GET | `/api/flavor-notes/{id}/` | одна нота |
| GET | `/api/flavor-notes/{id}/brands/` | в каких сортах она встречается, в каком слое и с какой интенсивностью |
| POST, PUT, PATCH, DELETE | `/api/flavor-notes/…` | стандартное редактирование |

### Блюда и пары

Оба набора только для чтения. Редактируются через Django-админку или CSV.

| Метод | Адрес | Фильтры |
|-------|-------|---------|
| GET | `/api/dishes/` | `cuisine`, `dominant_taste`, `weight`, `fat_level`, `q` |
| GET | `/api/dishes/{id}/` | - |
| GET | `/api/pairings/` | `brand_id`, `brand_name`, `dish_id`, `dish_name`, `pairing_type` |
| GET | `/api/pairings/{id}/` | - |

Пары отсортированы по убыванию оценки. Запрос `/api/pairings/?dish_name=шашлык` сразу даёт ответ на вопрос «что взять к шашлыку».

Значения фильтров можно писать в любом регистре: `?cuisine=kz` и `?cuisine=KZ` работают одинаково.

### Лендинг

| Метод | Адрес | Что делает |
|-------|-------|-----------|
| GET | `/api/landing/` | всё для главной страницы одним запросом |
| GET | `/api/courses/` | уровни Школы сомелье |
| GET | `/api/team/` | команда |

`/api/landing/` возвращает описание проекта, цитату, счётчики (сорта, ноты, профили, курсы, участники), курсы, команду и описание трёх слоёв пирамиды с цветами. Ответ кэшируется на пять минут, потому что главная открывается чаще всего, а данные на ней меняются редко.

### Кабинет сомелье

Отдельные эндпоинты под экран, где сомелье заполняет пирамиды. Стандартного CRUD там не хватало: пирамиду удобнее сохранять целиком, а не по одной ноте.

| Метод | Адрес | Что делает |
|-------|-------|-----------|
| GET | `/api/admin/brands/` | все сорта со статусом пирамиды, без пагинации |
| POST | `/api/admin/brands/` | создать сорт |
| PUT | `/api/admin/flavor-profiles/` | заменить пирамиду сорта целиком |
| PUT | `/api/admin/serving-recommendations/` | создать или обновить рекомендации по подаче |
| POST, PATCH, DELETE | `/api/admin/flavor-notes/` | создать, изменить (id в теле) или удалить ноту (`?id=`) |

Не путать с `/admin/` без префикса `api` - это обычная Django-админка.

Тело запроса на сохранение пирамиды:

```json
{
  "brand_id": "dddbfd41-1b09-40bc-9504-3a63a415f7a3",
  "notes": [
    { "flavor_note_id": "4aa9eac8-b4ed-4103-b3e0-d0273c12ce94", "layer": "TOP", "intensity": 6, "sommelier_note": "Благородный хмель" },
    { "flavor_note_id": "c411e6af-71fb-47dc-b610-ba47f26c8077", "layer": "HEART", "intensity": 6 },
    { "flavor_note_id": "a1f011e4-bb61-4e42-ad6e-3126cb22e603", "layer": "BASE", "intensity": 7 }
  ]
}
```

Интенсивность принимается только от 1 до 10. В ответе приходит список предупреждений - API не отказывает, а подсказывает:

```json
{ "ok": true, "warnings": ["Не заполнены слои: BASE"], "profile": { "complete": false } }
```

Предупреждение появится, если какой-то слой остался пустым или если нота из справочника `TOP` поставлена, например, в слой `BASE`. Запрос при этом не блокируется: окончательное решение остаётся за сомелье.

### Служебные

| Метод | Адрес | Что делает |
|-------|-------|-----------|
| GET | `/api/health/` | отвечает `{"ok": true}`, если сервер жив |
| GET | `/api/seed/` | загружает демо-данные, то же самое, что команда `load_flavor_data` |

## 7. Как запустить локально

Нужны Python 3.9 или новее и PostgreSQL.

1. Создать базу. По умолчанию проект ищет базу `app_db` с пользователем `postgres` и паролем `postgres` на `127.0.0.1:5432`.

```bash
createdb app_db
```

2. Поставить зависимости и применить миграции.

```bash
cd backend
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
```

3. Загрузить данные и запустить сервер.

```bash
python manage.py load_flavor_data
python manage.py runserver
```

После этого:

- API - http://127.0.0.1:8000/api/ (в браузере откроется страница DRF, где запросы можно пробовать руками);
- проверка, что всё живо - http://127.0.0.1:8000/api/health/;
- Django-админка - http://127.0.0.1:8000/admin/, для входа нужен `python manage.py createsuperuser`.

Если база у вас называется иначе или пароль другой, поменяйте это через переменные окружения, код трогать не надо:

| Переменная | По умолчанию | Зачем |
|------------|--------------|-------|
| `DB_NAME` | `app_db` | имя базы |
| `DB_USER` | `postgres` | пользователь |
| `DB_PASSWORD` | `postgres` | пароль |
| `DB_HOST` | `127.0.0.1` | хост |
| `DB_PORT` | `5432` | порт |
| `DJANGO_SECRET_KEY` | тестовый ключ | на сервере обязательно заменить |
| `DJANGO_DEBUG` | `True` | на сервере - `False` |
| `DJANGO_ALLOWED_HOSTS` | `*` | домены через запятую |

## 8. Откуда берутся данные

Исходники лежат в `backend/api/fixtures/` в виде CSV. Их можно открыть и поправить в Excel или Google Sheets, программировать для этого не нужно.

| Команда | Что делает |
|---------|-----------|
| `python manage.py load_flavor_data` | основная. Создаёт 31 ноту, 17 сортов с пирамидами (70 связей) и подачей, 50 блюд, в конце сама вызывает загрузку пар |
| `python manage.py load_food_pairings` | перезаливает только пары из `food_pairings.csv` |
| `python manage.py seed` | старый демо-набор с вымышленными сортами. Остался с первой версии, нужен только ради курсов и команды |

`load_flavor_data` можно запускать сколько угодно раз: записи ищутся по названию и обновляются, дубликаты не появляются. При этом команда удаляет сорта, которых нет в списке из 17, то есть убирает из базы демо-сорта старого набора.

Команда `seed` сначала очищает ноты, сорта и профили, а потом заливает свои. Запускать её поверх реальных данных не стоит. Если нужны курсы и команда на лендинге, порядок такой: сначала `seed`, потом `load_flavor_data`.

Пирамиды 17 сортов сейчас - черновик. Ноты и интенсивности проставлены по стилю, крепости и открытым описаниям сортов, без дегустации. Окончательные значения должен выставить сомелье, кабинет сомелье сделан именно для этого.

## 9. Заметки по реализации

Несколько решений, которые со стороны не очевидны.

**Три сериализатора для одного сорта.** В списке нужен лёгкий ответ со счётчиками, в карточке - полная пирамида, при создании - только редактируемые поля. Поэтому есть `BrandListSerializer`, `BrandDetailSerializer` и `BrandCreateUpdateSerializer`, а нужный выбирается в `get_serializer_class()` по типу действия.

**Запросы к базе.** В `BrandViewSet` стоит `prefetch_related('flavor_profiles__flavor_note', 'serving_recommendation')`. Без него Django ходил бы в базу отдельно за профилями каждого сорта, и список из 17 сортов стоил бы несколько десятков запросов. Сейчас их пять, мы проверяли. В парах по той же причине стоит `select_related('brand', 'dish')`.

**Пирамида сохраняется целиком.** `PUT /api/admin/flavor-profiles/` удаляет старые записи сорта и создаёт новые. Это проще и надёжнее, чем вычислять разницу между старым и новым состоянием, а пирамида маленькая - 4-8 нот.

**В пирамиде id - это id ноты, а не записи профиля.** Фронту нужен именно он, чтобы по клику на ноту открыть её страницу в справочнике.

**Ссылки на фото абсолютные.** Сериализатор сам достраивает `http://хост/media/brands/...`, потому что фронт и бэкенд живут на разных портах и относительный путь на фронте не сработал бы.

**Первый прототип был на Next.js.** Он лежит в папке `flavor-tree-backend-development-2/` (Next.js, Drizzle ORM, PostgreSQL). Адреса и формат ответов в Django сохранены те же, чтобы фронт не пришлось переписывать. Django-версия ушла дальше: в ней есть готовая админка, через которую данные можно править без разработчика, а также блюда и пары, которых в прототипе нет.

## 10. Что пока не сделано

Перечисляем честно, чтобы это не стало сюрпризом.

- **Ключ ИИ не подключен.** Без `ANTHROPIC_API_KEY` фото блюд не распознаются, чат и подбор пар работают по правилам. Ответ настоящей модели проверен только в тестах на подставных ответах.
- **Ограничения по частоте на Vercel считаются в памяти каждого экземпляра.** Для пилота нужен общий кеш. Дневной лимит обращений к ИИ уже хранится в базе.
- **Нет безалкогольных сортов и крепость заполнена у 2 сортов из 14.** Ждем официальные данные.
- **Пирамиды сортов - черновик.** Ноты расставлены без дегустации, их должен проверить сомелье.
- **Модели QRCode и AnonymousSession не используются.** Стол гостя передается в ссылке меню (`?table=7`).
- **Оплаты нет.** Заказ уходит в заведение, оплата остается за официантом.
- **Версии зависимостей не закреплены точно.** В `requirements.txt` стоят границы "от и до".

### Правила, которые важно знать

- **Пары.** У пары есть источник: сомелье или ИИ. Пары сомелье всегда идут первыми. Любая правка пары сомелье или модератором делает ее парой сомелье.
- **Тест.** `GET /api/quiz/<ступень>/` отдает 7 случайных вопросов из банка ступени. Проверяются только присланные вопросы, но прислать меньше семи нельзя.
- **Баллы.** Не хранятся отдельной суммой, считаются из событий: уроки, сданные ступени, отметки сортов, оценки пар. Остаток равен заработанному минус списанное на награды.
- **Отметки сортов.** Одна отметка на сорт. Не больше двух новых сортов в день: третья получит ответ 429.
- **Награды.** Название и описание проверяются на слова про алкоголь. Обмен баллов идет под блокировкой строки пользователя, повторный запрос отдает тот же код.
- **Заказы.** У позиции есть поле `via`: откуда гость ее добавил. Демо-заказы (`is_demo`) не видны в списке заказов и подписаны в аналитике.
- **Что слышат гости.** Сводка по сорту отдается от 3 отметок.
- **ИИ.** Распознанные блюда ничего не сохраняют: администратор проверяет список и отправляет его в `/api/dishes/import/`. Есть дневной лимит обращений и ограничения по частоте.

## Витрина: картинки и настройки

Эти модели появились вместе с мастером подбора и новой страницей сорта.
Всё, что ниже, редактируется в админке без участия разработчика.

### FlavorNote.image - «Фото вкуса»

Картинка ингредиента на прозрачном фоне: ромашка, колос, шишка хмеля,
сота мёда. На странице сорта такие фото встают кружками вокруг бутылки -
вместо emoji. Если поле пустое, остаётся emoji из поля «Иконка».

### Brand.accent_color и Brand.tagline

`accent_color` - HEX вида `#F5A623`. Задаёт подложку страницы сорта и
свечение за бутылкой, поэтому каждый сорт выглядит по-своему при одной
вёрстке. Пусто - берётся цвет темы сайта.

`tagline` - строка над названием, например «Классика пильзнера».

### FoodIcon - «Иллюстрации блюд»

Картинки характеристик блюда. Ключ обязан совпадать с кодом, иначе
картинка не подхватится и останется emoji:

| Тип | Коды |
|-----|------|
| CATEGORY | MEAT, SALAD, SOUP, ASIAN, SEAFOOD, PIZZA, STREET, SIDES, DESSERT, SNACK |
| COOKING | FRIED, GRILLED, BAKED, BOILED, STEAMED, RAW, CURED, FERMENTED |
| TASTE | SALTY, SWEET, SOUR, BITTER, UMAMI, SPICY, MIXED |
| WEIGHT | LIGHT, MEDIUM, HEAVY |

Используются в двух местах: на кружках мастера подбора и значками под
объяснением на карточке пары.

### SiteSettings - «Настройки витрины»

Запись одна на весь сайт, вторую добавить нельзя.

| Поле | Что делает |
|------|------------|
| `alternatives_count` | Сколько сортов показывать кроме лучшего. По умолчанию 3 |
| `min_score_to_show` | Пары с оценкой ниже в подбор не попадают |
| `show_wheat_decor` | Колосья по краям страницы |
| `pairing_intro` | Подпись над списком пар |
